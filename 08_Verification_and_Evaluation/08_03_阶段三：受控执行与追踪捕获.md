# 08.03 阶段三：受控执行与追踪捕获

第三阶段回答：**执行过程中发生了什么？** 传统 LLM 评估的证据可能只是单一的输入-输出对；智能体评估中，追踪是**多步轨迹**——模型观察状态、推理、调用工具、接收工具输出、修改环境、处理错误并最终终止。

## 受控 Rollout 与可复现执行

**Rollout** 是智能体评估的基本单元，包含：任务、模型配置、执行环境配置、动作序列、中间观察、最终状态和评分结果。

**受控 rollout** 固定以下关键变异来源：

- 环境状态
- 工具可用性
- 超时
- 预算
- 权限策略
- 评估器版本

当非确定性仍然存在时，重复 rollout 可以暴露方差，而非将其隐藏在单一分数背后。

| 系统 | 机制 |
|------|------|
| **SWE-agent** | 将仓库导航、文件编辑和测试执行作为交互循环的一部分 |
| **OpenHands** | 组合代码编辑、命令行执行、浏览器交互、沙箱执行和基准集成 |
| **SWE-ReX** | 抽象本地和远程沙箱 shell 环境，使执行后端可切换 |
| **LangChain 深度评估** | 分解为单步验证、完整轮次评估和多轮模拟（LangChain, 2025b） |

> **可复现性需要重放完整的模型-工具-环境交互，而非仅重运行一次模型调用。**

## 追踪原生的评估

追踪捕获将二元评分转化为**因果诊断**。追踪原生执行环境应记录：

- 模型输出
- 工具调用
- 工具结果
- 环境状态变化
- 上下文快照
- 错误、重试、恢复动作
- Token 使用、延迟、成本

**追踪可以区分表面上相似的失败**：一个智能体可能从未找到相关文件，另一个可能找到但生成了无效补丁。追踪还能揭示**不良成功**：基准利用、过多的工具调用或权限违例。

**HAL** 将日志和追踪作为标准化智能体评估的一级工件（Kapoor et al., 2025）。**R2E-Gym** 将可执行轨迹和混合验证器同时链接到测试时评估和训练时反馈（Jain et al., 2025）。

> 对执行环境工程而言，追踪不是辅助调试工件，而是**主要评估数据**。

## 成本、延迟和资源追踪

智能体评估应报告**不仅是质量，还有实现质量的成本**。长周期智能体可能通过消耗更多 token、调用更多工具、更频繁重试或使用更强模型来提高成功率。

评估应暴露**成功-成本-延迟前沿（frontier）**，而非仅按成功率排名。**HAL** 将智能体评估框定为标准化且成本感知的（Kapoor et al., 2025），**LangChain** 强调可复现环境和多粒度评估以比较成本-质量权衡（LangChain, 2025b）。
