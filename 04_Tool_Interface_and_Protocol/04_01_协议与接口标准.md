# 04.01 协议与接口标准

工具接口层的标准化正在快速演进。按**集成边界**而非供应商谱系或发布时间线对工具/接口标准进行分类，是一个更具解释力的组织原则。

## 四类集成边界

在此框架下，四个边界自然浮现，每个对应不同的互操作需求：

| 边界 | 含义 | 代表标准 |
|------|------|---------|
| **模型 ↔ 函数**（Model↔Function） | 结构化调用 | Function Calling（OpenAI） |
| **智能体 ↔ 外部能力**（Agent↔Capability） | 运行时与工具的解耦 | MCP、OpenAPI |
| **智能体 ↔ 智能体**（Agent↔Agent） | 跨进程委托 | A2A、ACP/ANP |
| **智能体 ↔ 仓库/环境**（Agent↔Repo/Env） | 版本控制的策略 | AGENTS.md / AGENT.md |

## 各标准详解

### MCP（Model Context Protocol）

MCP 已成为编码和企业智能体领域最显眼的工具集成基板，具有显式的**宿主-客户端-服务器架构**和基于 JSON-RPC 的类型化工具、资源和提示交换。

MCP 的实际价值不仅在于模式级互操作性，更在于**生态系统流动性**：智能体构建者可以复用不断扩展的服务器目录，而非为每个部署实现自定义连接器。

### A2A（Agent-to-Agent）

A2A 针对一个不同但相邻的边界：它不是将工具暴露给单个智能体进程，而是标准化**不透明智能体应用之间的通信**，包括：

- 通过 Agent Cards 进行服务发现
- 同步和流式交互支持
- 长周期任务协作

最近的协议综述将 MCP 和 A2A 置于互补角色：**MCP 主要用于工具/上下文访问，A2A 用于智能体间委托和协作**（Ehtesham et al., 2025）。

### Function Calling 与 OpenAPI

- **Function Calling**（OpenAI 风格）：通过 JSON Schema 和显式调用/返回来操作化工具调用（OpenAI, 2026c）
- **OpenAPI**：提供语言无关、机器可读的 API 契约，许多智能体框架将其用作工具生成和验证的源（OpenAPI Initiative, 2025）

### AGENTS.md / AGENT.md

仓库级指令文件提供了编码工具使用和工作流约束的**轻量级替代方案**，直接嵌入版本控制，降低代码智能体的设置摩擦。

## 标准间的互补关系

一个重要的认识是：经常被比较的标准实际上在单一执行环境中占据**互不重叠的角色**。例如 MCP vs A2A、Function Calling vs OpenAPI 的对比通常忽略它们服务于不同的集成边界。真实的智能体执行环境通常需要同时使用多个标准，分别覆盖不同的边界。
