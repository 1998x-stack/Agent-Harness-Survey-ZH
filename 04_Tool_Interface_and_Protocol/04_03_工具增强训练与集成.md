# 04.03 工具增强训练与集成

第三个方向从运行时编排转向**模型能力获取**——如何让模型本身学会使用工具。

## 模型侧进展

| 工作 | 贡献 |
|------|------|
| **Toolformer**（Schick et al., 2023） | 自监督增强：学习在生成过程中何时以及如何插入 API 调用 |
| **Gorilla / ToolLLM / ToolBench**（Patil et al., 2024b; Qin et al., 2024） | 更大的工具语料库、指令微调管线、以执行为中心的 API 使用监督 |
| **ToolkenGPT / CREATOR**（Hao et al., 2023; Qian et al., 2023b） | Token 级或控制器式集成，提升调用格式保真度和规划稳定性 |

## 生产执行环境中的集成

在工业生产环境中，这些模型侧进展通常与框架级运行时栈配对使用：

- **LangChain**
- **Semantic Kernel**
- **smolagents**

它们提供记忆抽象、路由中间件和工具适配器（LangChain, 2026c; Microsoft, 2026; Hugging Face, 2026）。

## 编码智能体的语义工具

编码智能体场景还暴露了**第二类、更具语义性的工具**：
- 静态分析器
- 类型检查器
- 基于求解器的验证器
- 证明助手
- 补丁等价性或故障定位检查器

**Ugare & Chandra (2026)** 将这一空间定义为**智能体代码推理（agentic code reasoning）**：智能体在不必然执行代码的情况下探索仓库并推理代码行为。其半形式化推理方法介于非结构化思维链和完全形式化验证之间，强制智能体陈述前提、追踪程序路径并推导显式结论，从而改进补丁等价性验证、故障定位和代码问答。

> 对工具层的启示：**自动化推理工具应返回带有证据的工件**——追踪、证明义务、反例或结构化证书——而非仅返回黑盒的是/否答案。

## 核心洞察

工具能力由以下因素**共同决定**：

```
工具能力 = 预训练信号 + 微调信号 + 接口模式质量 + 运行时选择策略
```

仅改进其中单一组件只能产生有限收益。这强调了工具层工程是一个集成系统问题。
