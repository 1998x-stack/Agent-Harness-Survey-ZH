工具接口与协议

T层定义了智能体如何发现能力、表示可调用的操作、跨异构运行时边界执行动作。它处于能力覆盖与决策质量之间的断层线上——过大的工具菜单降低可靠性，过小的约束限制能力。本章从协议标准、工具发现、模型训练和会话管理四个方向展开。

§4.1 协议与接口标准 按集成边界分类
按集成边界而非供应商谱系对工具标准分类，是更具解释力的组织原则。四个边界自然浮现，经常被比较的标准（如MCP vs A2A）实际上在单一执行环境中占据互不重叠的角色。

MCP · 生态系统流动性

宿主-客户端-服务器架构 + JSON-RPC类型化交换。实际价值不仅在于模式互操作——更在于生态系统流动性：可复用不断扩展的服务器目录，而非为每个部署实现自定义连接器。

A2A · 互补角色

标准化不透明智能体应用间通信——Agent Cards服务发现、同步/流式交互、长周期任务协作。MCP主要用于工具/上下文访问，A2A用于智能体间委托和协作。

一旦协议定义了如何发起调用，下一个瓶颈是哪些工具应该在每一步被呈现和选择。工具文档质量、检索和动态候选剪枝成为一阶决定因素。
§4.2 工具描述、发现与选择
关键研究发现：工具检索和调用质量在不同领域和查询形式下存在显著差异——注册表质量和检索感知编排是下游智能体成功的一阶决定因素。研究正从工具选择扩展到可复用技能的识别。
工具选择研究
  • EASYTOOL：大型工具清单中选合适工具的挑战
  • AnyTool · CRAFT：自动构建工具使用流水线，减少人工指定
  • MetaTool：基准评估揭示跨领域工具调用质量差异
  • MCP-Zero · ToolRet · ToolRegistry：检索感知编排 + 注册表质量
扩展到技能选择
  • SkillRouter (Zheng et al., 2026)：大规模技能选择
  • SkillRet (Cho et al., 2026)：从庞大重叠技能库中检索正确技能
原则一
"少而精的工具"优于暴力暴露
  • 缩小提示熵（prompt entropy）
  • 减少规划器分支因子（planner branching）
  • 降低 token 开销
原则二
发现管线必须是自适应的
  • 静态全局工具列表无法扩展到快速演进的仓库
  • 无法适应多租户企业部署
  • 必须根据上下文动态调整候选集
§4.3 工具增强训练与集成
从运行时编排转向模型能力获取——如何让模型本身学会何时以及如何使用工具。生产环境中，模型侧进展与框架级运行时栈（LangChain、Semantic Kernel、smolagents）配对使用。
Toolformer

自监督增强——学习在生成过程中何时以及如何插入API调用 (Schick et al., 2023)

Gorilla · ToolLLM

更大工具语料库、指令微调管线、以执行为中心的API使用监督 (Patil/Qin, 2024)

ToolkenGPT · CREATOR

Token级/控制器式集成，提升调用格式保真度和规划稳定性 (Hao/Qian, 2023)

智能体代码推理（Ugare & Chandra, 2026）：智能体在不必然执行代码的情况下探索仓库并推理代码行为。对工具层的启示——自动化推理工具应返回带有证据的工件（追踪、证明义务、反例、结构化证书），而非仅返回黑盒的是/否答案。

工具能力= 预训练信号+ 微调信号+ 接口模式质量+ 运行时选择策略

仅改进单一组件只能产生有限收益——工具层工程是一个集成系统问题。

§4.4 可扩展性与会话管理
有状态工具会话是双刃剑：改善连续性，但增加记账复杂性。三种典型失败模式和三项设计要求定义了生产级工具会话工程的核心关注点。
三种典型失败模式
  • 过期句柄：长时间运行后工具会话引用失效
  • 不一致的工具状态：重试时状态未正确同步
  • 上下文窗口饱和：冗长工具追踪填满窗口
三项设计要求
  • 显式生命周期控制：创建、使用、销毁、恢复——不隐式推给模型
  • 有界上下文注入：选择性、摘要化、渐进式策略
  • 可观测性错误归因：追踪到规划器逻辑 vs 接口/协议故障

生态系统级的全景策展可以帮助实践者快速映射可用选项。但基于基准的比较对于决定特定部署中应采用哪种协议和工具路由策略仍然不可或缺。
