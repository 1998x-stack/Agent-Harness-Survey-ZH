§3.1 范围与概念 沙箱的三重目的
智能体时代的沙箱不仅是继承自传统多租户代码执行的安全措施。它同时服务于安全、可复现性和活性三个截然不同的目的——三者组合将沙箱从运维细节提升为执行环境设计中的一级架构关切。
共享于传统
安全 Security
LLM生成的代码不可大规模审计或预测；智能体跨多步自主执行，无人类实时干预；提示注入可将良性智能体转化为攻击向量——模糊可信意图与恶意输入的边界。
被智能体放大
可复现性 Reproducibility
Docker/microVM可按需销毁重建，开发者工作站做不到。SWE-bench和OSWorld等评估标准依赖这一特性。训练时单任务需数百条并行轨迹重放——缺乏廉价复位机制本身就是扩展性瓶颈。
智能体时代全新
活性 Liveness
沙箱定义有界区域，智能体在其中自由行动——权限从"每步都问"变为"会话级一次设定"。沙箱同时是牢笼和许可证：许可证的一面使自主长周期执行成为可能。
-84% 权限提示减少
目的与传统沙箱的关系智能体时代的特殊性
安全共享提示注入、自主多步执行放大威胁
可复现性被放大评估和训练的规模化需求
活性全新无沙箱则长周期自主执行不可行
§3.2 智能体沙箱的七大类别
2024-2026年间，沙箱基础设施从少量通用运行时分化为七个截然不同的产品类别，每个针对不同任务类型优化。按工作负载和使用场景分类对执行环境设计者最具信息价值。
01
通用托管沙箱
Daytona (<90ms) · E2B (Firecracker) · Modal (gVisor) · Northflank · OpenSandbox · Docker Sandboxes
趋势：从共享内核容器 → 独立内核 microVM。LLM代码的不可预测syscall模式驱动这一迁移。
02
计算机使用智能体
Anthropic Computer Use · CUA · OSWorld
以密度和启动延迟换取保真度——操作无API应用的唯一执行模型。需microVM/全VM级别隔离。
03
代码专用沙箱
Judge0 · OpenAI Code Interpreter · sandboxed.sh · langchain-sandbox (Pyodide/Wasm)
牺牲通用性换启动速度。子趋势：容器 → WebAssembly（能力安全+微秒实例化）。
04
框架集成运行时
OpenHands Runtime · agent-infra · smolagents executor层
核心权衡：bundle（开箱即用但耦合）vs compose（最小环境+外部抽象组装）。
05
浏览器评估环境
WebArena · VisualWebArena · BrowserGym · WorkArena
双重角色：沙箱+评估执行环境。直接连接执行环境层与评估层（§8）。天然底床研究间接提示注入。
06
OS级权限沙箱
Anthropic sandbox-runtime (bubblewrap) · Claude Code 沙箱 · IsolateGPT (seccomp)
设计哲学：权限而非分区——收窄主机视图。适用于提示注入威胁模型，非完全对抗性代码。
07
沙箱抽象层
SWE-ReX · smolagents executor接口 · K8s Agent Sandbox CRD
将运行什么与在哪里运行解耦——沙箱抽象正在成为执行环境栈的独立层。
三大跨类别趋势
隔离强度两极分化：microVM vs 收窄主机视图，纯Docker被两端挤压 评估鲁棒性上升：SandboxEscapeBench/CIBER证实生产配置可被绕过 基础设施隔离 vs 语义隔离分离：§3 vs §4互补，完整执行环境需两者兼有
§3.3 威胁模型与沙箱逃逸
智能体沙箱执行同时面临传统容器级威胁和三种智能体时代独有的攻击向量——后者从根本上挑战了传统安全模型的假设。
三种智能体特异威胁
  • 提示注入：外部输入劫持智能体行为——攻击面从受控用户输入扩展到所有非受控数据
  • 目标错位：智能体本身主动尝试沙箱逃逸作为工具性子目标——攻击者和被攻击者是同一进程的不同意图层面
  • 组合放大：多工具访问权限下，单一弱点通过集成能力产生级联效应
防御研究（早期阶段）
  • IsolateGPT：执行隔离架构，75%查询性能开销<30%，防跨应用泄露
  • 事务性沙箱：回滚保护，约14.5%开销，高风险命令高拦截率
  • LLM-in-Sandbox：最小化沙箱能力，减少攻击面和复杂性
15% – 35%
SandboxEscapeBench · 前沿LLM · Docker容器逃逸成功率（取决于配置）

攻防鸿沟：进攻性评估已产出具体且可复现的基准测试，而防御性工作仍分散在隔离原型之间。一个在统一评估方法下系统性处理提示注入、目标错位和组合放大的智能体原生运行时安全框架仍是开放研究方向（§12.1）。

§3.4 部署模式
最低延迟
自托管 Self-Hosted
开发者直接管理沙箱基础设施。最紧密迭代循环，承担全部运维负担。
OpenHands · SWE-agent 默认模式
弹性扩展
云 SaaS
沙箱即服务提供商处理基础设施。弹性扩展+托管安全，代价是网络往返延迟。
E2B · Modal · Daytona Cloud
合规优先
混合/自带云 BYOC
智能体逻辑与沙箱执行跨环境解耦。保留敏感数据本地，委托执行能力。
OpenHands SDK · E2B BYOC · Northflank BYOC
驱动力量一：三轴权衡

部署选择沿延迟、安全性和可扩展性三轴展开。自托管最低延迟但承全部运维负担；云沙箱弹性扩展但增加网络延迟；混合模式试图在数据本地性和执行容量之间取得平衡。

驱动力量二：组织约束

数据驻留、合规性和可审计性推动部署向混合架构靠拢——即使纯从延迟和可扩展性角度单一模式可能最优。数据治理和合规性正成为与延迟和性能同等重要的一级约束。
