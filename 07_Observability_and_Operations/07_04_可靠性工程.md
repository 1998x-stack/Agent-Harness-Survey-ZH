# 07.04 可靠性工程

故障恢复、检查点/恢复、重试策略和会话恢复是执行环境级的关注点，决定长周期智能体能否在瞬态故障中存活。当智能体跨多个上下文窗口运行时，这些关注点变得尤为突出——每个新会话开始时对之前发生的一切毫无记忆（Anthropic, 2025d）。

## 四种反复出现的故障模式

Anthropic 将长周期编码智能体的失败模式归纳为四类：

| 故障模式 | 表现 |
|---------|------|
| **一次性完成整个任务** | 智能体试图单次处理过于复杂的任务 |
| **过早宣布完成** | 智能体未完成实质工作即声称项目完成 |
| **在会话间留下损坏状态** | 环境在两次会话之间处于不可用状态 |
| **未经测试标记完成** | 功能被标记为完成但未经过适当测试 |

## 初始化器 + 编码智能体：两阶段方案

Anthropic 通过执行环境设计而非模型改进来解决这些可靠性问题：

1. **初始化器智能体**：将任务分解为结构化功能列表，设置进度追踪工件（git 仓库、进度文件、初始化脚本）
2. **编码智能体**：逐功能增量工作，每次留下干净的交接状态

## 执行环境复杂度应跟踪模型能力

Anthropic 的 GAN 风格三角架构（规划器-生成器-评估器）引入了 sprint 契约和分离的自我评估（Anthropic, 2026c）。

> **关键原则**：当从 Opus 4.5 升级到 Opus 4.6 时，团队完全移除了 sprint 构造和上下文重置，成本从 **$200 降至 $125**，同时保持输出质量。

这说明一个普遍原则：**每个执行环境组件都编码了一个关于模型不能独立做什么的假设——这些假设会随着模型改进而过时。**

## Managed Agents 架构

Anthropic 的 Managed Agents 架构将系统解耦为三个独立可恢复的组件：

| 组件 | 角色 | 恢复机制 |
|------|------|---------|
| **大脑**（Harness + LLM） | 编排和推理 | `wake(sessionId)` 从会话日志最后事件恢复 |
| **双手**（Sandboxes + Tools） | 执行动作 | 工具调用失败 → 自动配置新沙箱 |
| **会话**（Durable Event Log） | 持久事件记录 | 不可变日志 |

凭证存储在外部保险库中，永不进入沙箱。这一架构将所有组件从"宠物"（不可替代、需人工维护的实例）转变为"牲畜"（可互换、自动重新配置）——这是**大规模可靠运行智能体的前提**。

## 故障分类学

| 工作 | 贡献 |
|------|------|
| **MAST**（Cemri et al., 2025） | 14 种故障模式，跨系统设计、智能体间错位和任务验证（κ=0.88） |
| **AgentErrorTaxonomy**（Zhu et al., 2025） | 按模块分解故障，揭示**错误传播是中心可靠性瓶颈**；AgentDebug 框架实现 26% 相对改进 |
| **Vinay（2025）** | 15 种生产部署特有的隐藏故障模式，含版本漂移、成本驱动的性能崩溃、多步推理漂移 |
| **QSAF**（Atta et al., 2025） | 认知退化的六阶段生命周期——**幻觉输出可被存入持久记忆并在未来会话中复用**，形成跨越会话边界的自我强化退化循环 |

## 分层检测策略

| 层级 | 方法 | 针对 |
|------|------|------|
| **轻量级规则检查** | 确定性检查 | 结构性故障（格式错误的工具调用、schema 违例） |
| **统计监控** | 指标趋势分析 | 性能漂移（延迟、token 使用、成本趋势） |
| **LLM 语义分析** | 模型判断 | 推理失败（幻觉、计划-动作错位、过早停止） |

**AgentFixer**（Mulian et al., 2026）在 IBM CUGA 生产系统上部署 15 个验证工具，实现 64-88% 的问题检出率，并发现 **38% 的任务失败源于解析错误**——这是完全可通过确定性检查解决的故障模式。
