# 03.02 智能体沙箱的七大类别

2024-2026 年间，智能体沙箱基础设施从少量通用运行时迅速分化为多个截然不同的产品类别，每个类别针对不同的智能体任务类型进行了优化。我们按**工作负载和使用场景**将其分为七大类别，这一维度对选择系统的执行环境设计者最具信息价值。

**隔离技术**（容器、gVisor、Firecracker microVM、Kata Containers、WebAssembly、bubblewrap/Seatbelt 等 OS 级原语）在各小节内部作为设计属性讨论，而非顶层分类——因为同一隔离原语可跨不同工作负载复用。

## 3.2.1 通用托管沙箱

提供商业或开源的沙箱即服务平台，通过 API 接口暴露任意 OCI 容器镜像，支持 shell、文件系统、网络和解释器。

| 系统 | 隔离技术 | 特点 |
|------|---------|------|
| **Daytona** | 容器（可选 Kata） | 从开发者环境转向智能体沙箱，< 90ms 冷启动 |
| **E2B** | Firecracker microVM | 专为智能体设计的沙箱 |
| **Modal** | gVisor | Python 平台，大规模自动扩缩容 |
| **Northflank** | Kata/Firecracker/gVisor | 唯一支持多后端同时运行的平台 |
| **OpenSandbox**（阿里） | — | 开源通用沙箱 |
| **Docker Sandboxes** | microVM | Docker 官方 2025 年 microVM 产品 |

**设计趋同点**：
- 默认临时语义 + 可选持久会话
- Python/TypeScript SDK 接口
- 支持任意 OCI 镜像

**分歧点**：隔离强度与运维模式。从内核容器隔离向**独立内核 microVM 隔离**迁移的趋势明显，驱动力是 LLM 生成代码具有不可预测的系统调用模式。

## 3.2.2 计算机使用智能体基础设施

一种独特的执行模型：智能体通过模拟鼠标、键盘和屏幕观察与图形界面交互，而非通过 API 或 shell 命令。

| 系统 | 类型 | 特点 |
|------|------|------|
| **Anthropic Computer Use** | 商业旗舰 | Claude 直接操作桌面环境 |
| **CUA** | 开源 | 计算机使用智能体基础设施 |
| **OSWorld** | VM 环境 | 兼具评估执行环境（§8）和参考计算机使用沙箱双重角色 |

这些系统在沙箱内打包完整或近完整的桌面环境（通常通过 Xvfb + 窗口管理器或完整 VM），暴露像素坐标和按键动作给智能体。动作空间远大于基于 API 的类别，但可靠性依赖视觉定位，且完整的 OS 攻击面要求更强的隔离（通常为 microVM 或全 VM）。

> 与通用托管沙箱（§3.2.1）相比，计算机使用沙箱以密度和启动延迟换取保真度：完整桌面环境启动更重、更难复用，但它是智能体操作无 API 应用的**唯一执行模型**。

## 3.2.3 代码专用沙箱

轻量级环境，针对代码生成、评估和数据分析优化，而非通用 shell 访问。

| 系统 | 定位 | 技术特点 |
|------|------|---------|
| **Judge0** | 代码评估沙箱 | 广泛用于编码智能体评估管线 |
| **OpenAI Code Interpreter** | 生产级沙箱 Python | ChatGPT 高级数据分析的底层 |
| **sandboxed.sh** | Shell 沙箱 | 面向编码智能体 |
| **langchain-sandbox** | Pyodide/WebAssembly | 本地无容器沙箱 Python（NVIDIA 也倡导此方案） |

**设计取舍**：牺牲工作负载通用性，换取启动速度、评估吞吐量和更简单的威胁模型。

**值得注意的子趋势**：从基于容器的代码沙箱向**基于 WebAssembly 的沙箱**迁移。WebAssembly 提供基于能力的安全模型、确定性执行和微秒级实例化，代价是受限的 Python 标准库和原生扩展支持。

## 3.2.4 框架集成运行时

捆绑在更广泛的智能体框架内部的执行环境，而非作为独立沙箱产品暴露。

| 系统 | 打包内容 |
|------|---------|
| **OpenHands Runtime** | Docker + bash + IPython + Chromium 浏览器 + API 服务器（单一镜像） |
| **agent-infra sandbox** | 浏览器 + shell + 文件系统 + MCP + VSCode（一体化设计） |
| **smolagents executor 层** | 框架内实现 local/Docker/E2B/Modal/WebAssembly 执行 |

**核心权衡**：打包（bundle）vs 组装（compose）。框架集成运行时优先开箱即用的能力覆盖，代价是更大的镜像体积、更慢的启动速度和与单一框架抽象的紧密耦合。通用沙箱（§3.2.1）则采取相反路径：最小环境 + 外部抽象组装。

> 组装方法能否在长期取代捆绑运行时，取决于 MCP 等标准能否降低运行时组装能力的代价。

## 3.2.5 浏览器评估环境

兼具沙箱和评估执行环境的双重角色。

| 系统 | 特点 |
|------|------|
| **WebArena** | 自托管真实 Web 应用集群 + Playwright 交互 |
| **VisualWebArena** | WebArena 的多模态视觉定位扩展 |
| **BrowserGym + WorkArena** | 标准化 gym 风格接口用于浏览器智能体执行和基准测试 |

**双重功能**：提供隔离的 Web 执行环境（沙箱角色），同时提供带自动化评估的可复现任务定义（评估角色）。这使它们区别于桌面级的计算机使用类别（§3.2.2），并在执行环境（本章）和评估基础设施（§8）之间建立了直接接口。

浏览器环境还暴露了独特的威胁面：由于浏览器摄入不受信任的 Web 内容，它们成为研究间接提示注入和多模态红队攻击的天然底床。

## 3.2.6 OS 级权限沙箱

使用操作系统原语（Linux 上的 `bubblewrap`、macOS 上的 Seatbelt、`seccomp-bpf` 系统调用过滤）而非容器、VM 或用户空间内核实现细粒度的文件系统和网络隔离。

| 系统 | 机制 |
|------|------|
| **Anthropic sandbox-runtime** | 开源 npm 包，通过 `bubblewrap` + 本地 HTTP/SOCKS5 代理强制执行文件系统和网络白名单 |
| **Claude Code 沙箱功能** | 消费上述运行时限制 bash 工具的文件系统和网络访问 |
| **IsolateGPT** | 使用 `seccomp` 和 `setrlimit` 在工具调用 LLM 应用中强制隔离 |

**设计哲学**：**权限**（permission），而非分区（partition）。目标不是为每个会话提供全新 OS 镜像，而是给智能体一个**对现有主机的收窄视图**，使提示注入或幻觉产生的命令无法修改敏感文件或窃取数据。

> 由于共享主机内核，OS 级权限沙箱对对抗性代码的隔离弱于 microVM 沙箱（§3.2.1）；它们适用于威胁模型为提示注入而非完全对抗性代码的场景。

## 3.2.7 沙箱抽象层

本身不是沙箱，而是**将多个沙箱后端统一在单一 API 后的接口**，使执行环境可以在不重写智能体代码的情况下切换执行基板。

| 系统 | 统一的后端 |
|------|----------|
| **SWE-ReX** | Docker、AWS Fargate、Modal、Daytona |
| **smolagents executor 接口** | local、e2b、modal、docker、blaxel、wasm |
| **K8s Agent Sandbox CRD** | gVisor、Kata Containers（通过声明式 API 以插件形式切换） |

这一类别的出现反映了对**执行基础设施应可替换**这一认知的成熟。将特定沙箱 API 硬编码的执行环境会将其编排逻辑耦合到单一供应商的短暂产品；抽象层则将智能体**运行什么**与**在哪里运行**解耦。

研究项目（SWE-ReX）、框架嵌入接口（smolagents executor）和新兴基础设施标准（Kubernetes agent-sandbox CRD）之间的趋同表明：**沙箱抽象正在成为智能体执行环境栈的一个独立层**，而非单个系统的功能特性。

## 跨类别综合趋势

七大类别揭示了三个跨领域的趋势：

### 趋势一：隔离强度的两极分化

通用托管沙箱（§3.2.1）从共享内核容器向独立内核 microVM 迁移，而 OS 级权限沙箱（§3.2.6）则完全放弃独立环境，转而收窄主机视图。**纯 Docker 容器的中间地带正从两端被挤压**，两端的选择反映的是威胁模型（完全对抗性代码 vs 提示注入但其他方面合作的代码），而非通用的技术偏好。

### 趋势二：评估鲁棒性上升为一级关切

SandboxEscapeBench（Marchand et al., 2026）和 CIBER（Ba et al., 2026）等基准测试表明，当前在生产中部署的沙箱配置**部分可被前沿模型绕过**。

### 趋势三：基础设施级隔离与语义级隔离的分离

- **基础设施级隔离**（本章内容）：约束动作执行后的爆炸半径
- **语义/能力级隔离**（工具调用层）：约束哪些动作首先被允许（CaMeL 的控制流完整性设计、Progent 的可编程权限控制，属于 §4）

两者互补：完整智能体执行环境需要两者兼有。
